I am integrating an offerwall from PLAYNDGAIN into my product. Build the
server-side callback endpoint for me, in the language and framework I use
here. Follow this contract exactly. Do not invent parameters, and do not
weaken any of the rules below to make the code shorter.

WHAT I ALREADY HAVE
- App ID: YOUR_APP_ID (public, goes in the wall URL)
- App secret: read it from the environment variable PLAYNDGAIN_SECRET.
  Never write it into source code, a client bundle, or a log line.
- The wall is embedded as an iframe:
  <iframe src="{APP_URL}/wall?appid=YOUR_APP_ID&userid=USER_ID"
          width="100%" height="800" frameborder="0"
          allow="clipboard-write" title="Earn coins"></iframe>
  USER_ID is my own stable identifier for the player. It is echoed back on
  every conversion as user_id.

WHAT ARRIVES AT MY ENDPOINT
When a player completes an offer, PLAYNDGAIN sends one HTTP request (GET by
default; I can set POST in my dashboard) to a callback URL I configure. I
choose the parameter names in that URL; each one is filled from a macro:

  {user_id}          string   my identifier for the player
  {trans_id}         string   unique per conversion, stable across retries
  {offer_id}         int      may be empty; never key on it
  {offer_name}       string   URL-encoded
  {payout_usd}       decimal  what I earn, six decimals, e.g. 0.130000
  {currency_amount}  decimal  what the player gets in my currency, e.g. 130.00
  {app_id}           int
  {country}          string   ISO-2
  {ip}               string
  {status}           string   "credited" or "reversed", nothing else
  {timestamp}        int      unix seconds, regenerated on every attempt
  {signature}        string   see below

Propose a callback URL for me in this shape, using the parameter names you
choose, and tell me to paste it into Apps > Postback in the dashboard:

  https://<my domain>/<path>?user_id={user_id}&trans_id={trans_id}
    &payout={payout_usd}&amount={currency_amount}&status={status}
    &sig={signature}

RULE 1: VERIFY THE SIGNATURE BEFORE DOING ANYTHING
  signature = sha256( trans_id + payout_usd + app_secret )
Concatenate the three strings with nothing between them and hex-encode the
digest. payout_usd must be hashed EXACTLY as it arrived in the query string:
six decimal places, and a leading minus on a reversal. Do not parse it to a
number, round it, reformat it, or URL-decode it before hashing. Compare with
a constant-time function (hash_equals, timingSafeEqual, hmac.compare_digest,
subtle.ConstantTimeCompare, or the equivalent). On mismatch respond 403 with
a short plain-text reason and stop.

RULE 2: DEDUPE WITH A UNIQUE INDEX, NOT A LOOKUP
Deliveries are retried up to six times on any non-2xx response, so the same
request WILL arrive more than once, sometimes concurrently. Store one row per
(trans_id, status) with a UNIQUE index on that pair. Insert first; if the
insert fails with a uniqueness violation, respond 200 and stop. Do not
SELECT-then-INSERT; two concurrent retries both pass the check and the
player is paid twice. The key must be the PAIR, never trans_id alone,
because a reversal reuses the trans_id of the credit it undoes.

RULE 3: HANDLE REVERSALS
When status is "reversed", payout_usd and currency_amount are NEGATIVE and
trans_id is the ORIGINAL credit's id. Deduct the currency from the player.
Branch on the sign of currency_amount, never treat it as unsigned. Ask me
which policy I want when the player has already spent the coins: allow a
negative balance, cap at zero, or cap at zero and flag the account. Default
to "allow negative" if I do not answer.

RULE 4: DO THE INSERT AND THE BALANCE CHANGE IN ONE DATABASE TRANSACTION
A crash between them must not leave a recorded transaction with no payout,
or a payout with no record.

RULE 5: ANSWER 2xx
Return 200 with a short plain-text body on success AND on a duplicate. Any
4xx, 5xx, redirect, or timeout over 15 seconds is treated as a failure and
retried. Do not redirect HTTP to HTTPS on this path; configure the final URL.
The response body is stored and shown to me, so put a useful one-line
message in it. Never echo the secret.

DELIVERABLES
1. The endpoint, complete and runnable, with the four rules in this order:
   verify, insert (dedupe), branch on sign and adjust balance, respond.
2. The migration or schema for the transactions table with the unique index
   on (trans_id, status).
3. The callback URL to paste into the dashboard.
4. A test script (curl or my test framework) that:
   a. signs and sends one credited request and asserts the balance rose once;
   b. sends the identical request again and asserts the balance did not move
      and the response was still 200;
   c. negates payout and amount, recomputes the signature over the negative
      payout string, sends it with status=reversed, and asserts the balance
      went DOWN.
5. A short note on how to run it against test mode: in the dashboard turn on
   Apps > Settings > Test mode, load the wall with a throwaway userid, click
   the Test Offer, and read the attempt in Postback Reports.
